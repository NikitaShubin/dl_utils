# 📘 Правила документации

Документ задаёт, как писать и обновлять документацию проекта. Сначала идут
общие правила, не зависящие от репозитория, затем профиль `dl_utils` с
конкретными путями и словарём эмодзи.

Правила задают обязательный минимум и разумный максимум. Дополнительные
разделы допустимы, если они полезны, не дублируют другие страницы и не
противоречат правилам. Закрытого списка максимумов нет: ориентир — польза для
читателя.

## 🌍 Общие правила

### Назначение и область

Правила действуют для пользовательской документации: `README.md` и `docs/**`.
Файлы инструкций агенту (`AGENTS.md` и аналоги) — не пользовательские страницы;
на них правила не распространяются. Сторонние и сгенерированные файлы не
проверяются.

Цель страницы — чтобы новый читатель или агент понял сущность и смог ей
воспользоваться без чтения исходников.

### Термины

- **Страница** — весь `.md`-файл.
- **Раздел** — заголовок `##`.
- **Подраздел** — заголовок `###`.
- **Пример** — короткий блок кода с пояснением: однострочным комментарием или
  фразой перед блоком.
- **Сущность** — модуль, класс, функция, скрипт, команда или иной объект,
  который раскрывает страница.
- **Точка входа** — корневой `README.md`, единственная страница-каталог проекта.

### Типы страниц

Тип выбирается по назначению страницы, а не по её расположению. Ниже —
обязательный порядок разделов; необязательные помечены явно.

**Точка входа.** Каталог проекта и минимальный быстрый старт:

```text
# <эмодзи> <проект>: назначение

1–3 строки: что это и как подключить.

## 🚀 Быстрый старт
## 🧩 Основные модули
## 📚 Документация
## ❓ FAQ
```

**Инструмент или чекер.** Узкая задача с командами и флагами:

```text
# <эмодзи> <инструмент>: назначение

1–2 строки: что проверяет или делает.

## 🚀 Примеры
## ⚖️ Режимы правил        (если есть)
## 🎛️ Флаги                (если есть)
## 🔧 Что происходит внутри
## ⚠️ Ограничения
```

**Модуль или справочник.** Несколько сущностей и подробное описание:

```text
# <эмодзи> <module.py> — назначение

1–2 строки: что это и зачем.

## 🚀 Примеры
## <эмодзи> <Группы сущностей>
## 🔧 Как устроено          (необязательно)
## ⚠️ Ограничения
```

**Концепция.** Объяснение принципов и решений:

```text
# <эмодзи> <тезис>

1–3 строки: что объясняет страница.

## <эмодзи> <Принцип 1>
Конкретный пример или иллюстрация.
## <эмодзи> <Принцип 2>
...
## ⚠️ Ограничения          (если есть)
```

**Руководство или сценарий.** Пошаговое использование:

```text
# <эмодзи> <сценарий>

1–2 строки: что и когда делать.

## 🚀 Запустить
## <эмодзи> <Шаги или компоненты>
## ⚠️ Ограничения
```

### Примеры

Если тип страницы предусматривает раздел примеров, он идёт сразу после
вводного абзаца, который определяет сущность. В README он называется
`Быстрый старт`, в руководстве — `Запустить`. Режимы, флаги, устройство и
ограничения — после примеров.

- На каждую сущность, которую страница обещает раскрыть, дай хотя бы один
  пример.
- Близкие операции объединяй в один пример.
- Пример — отдельный блок кода; отдельный заголовок для примера не нужен.
- Смысл примера задаёт короткая фраза перед блоком или однострочный
  комментарий внутри. Не дублируй одно другим.
- В общем разделе `Примеры` предпочитай комментарии внутри блока: так
  примеры компактнее.
- Комментарий объясняет задачу, а не пересказывает код.
- Пример должен быть минимальным рабочим; полный API не перечисляй.
- Используй реальные имена, а не `foo` и `bar`.
- Указывай язык блока кода.
- Пример длиннее 10–15 строк сократи или разбей.
- В разделах сущностей допустимы более подробные примеры; общий раздел
  `Примеры` остаётся точкой входа.

Пример правильного оформления:

```bash
# Проверить весь проект
./check-infra.sh ~/my_project

# Проверить отдельные файлы
./check-infra.sh docker docs README.md
```

### Заголовки и эмодзи

- Один `#` на страницу: `<эмодзи> <название>`.
- `##` — основные разделы, с эмодзи; для повторяющихся разделов используй
  словарь профиля.
- `###` — подразделы без эмодзи, только когда они действительно нужны;
  исключения — в профиле.
- Не создавай заголовок для каждого блока кода.
- Не пропускай уровни заголовков.
- Эмодзи допустимы только в `#`, `##` и `<summary>`; в тексте, списках и
  коде — нет, кроме исключений профиля.
- `<summary>` рендерится как заголовок, поэтому эмодзи в нём допустим.
- Один и тот же смысл обозначай одним и тем же эмодзи.
- В заголовке — один эмодзи, без точки в конце.
- Заголовок должен быть информативным: «Разное» допустимо только для
  действительно разнородного раздела.

### Текст, код и ссылки

- Проза — русская, идентификаторы — английские.
- Инструкции — в императиве. Пользовательские страницы обращаются к читателю
  на «вы»; этот документ и `AGENTS.md` — к агенту на «ты».
- Держи абзацы короткими: одна мысль на абзац.
- Сначала объясняй «зачем», затем «как».
- Избегай маркетинговых прилагательных, статусов, бейджей и дат.
- Определяй термин при первом употреблении; связывай страницы ссылками.
- Внутренние ссылки — относительные; внешние — с описательным текстом.
- Блоки кода — с языком; команды выполняются из корня проекта, если не
  указано иное.
- Длина строки — до 88 символов.
- Списки предпочитай таблицам; таблицу используй, когда она яснее.
- Жирный лид перед списком — подпись группы, а не заголовок; допустим, если
  группа не заслуживает отдельного `##`.
- Один смысл — в одном месте; вместо копии дай ссылку.

### Обновление документации

- Меняешь поведение кода — проверь, не противоречит ли документация
  реальности. Значимые изменения отражай в соответствующих страницах.
- Добавляешь публичную сущность — оцени её значимость и необходимость
  описания.
- Исправляешь баг или делаешь внутренний рефакторинг — документация обычно
  не меняется, но противоречий в ней быть не должно.
- Источник правды — фактическое поведение кода. Если оно ошибочно, сначала
  исправь код, затем документацию.
- Меняешь правила — сначала обнови этот документ, затем приведи страницы в
  соответствие, проверь результат и только потом фиксируй изменения.

### Как менять правила

- Добавляй правило только при реальной проблеме; минимальный набор важнее
  полноты.
- Сначала сформулируй правило, затем примени его к документации, проверь
  результат и зафиксируй вместе с правилом.
- Общая часть остаётся независимой от проекта; конкретика уходит в профиль.

### Чек-лист агента

- [ ] Тип страницы определён.
- [ ] Вступление объясняет сущность за 1–3 строки.
- [ ] Если тип страницы требует примеров, они идут сразу после вступления.
- [ ] На каждую обещанную сущность есть пример.
- [ ] Детали, режимы и флаги идут после примеров.
- [ ] `Ограничения` стоят в конце, если они есть.
- [ ] `#` и `##` с эмодзи, `###` без эмодзи (кроме исключений профиля).
- [ ] Дополнительные разделы не дублируют другие страницы.
- [ ] Нет маркетинга, статусов и бейджей.
- [ ] Ссылки относительные, блоки кода с языком.
- [ ] `markdownlint` проходит.
- [ ] Правила обновлены, если менялось правило.

## 🧰 Профиль dl_utils

### Карта страниц

- `README.md` — точка входа.
- `docs/about.md`, `docs/development.md` — концепция.
- `docs/check.md`, `docs/check-py.md`, `docs/check-infra.md` — инструмент.
- `docs/docker.md` — руководство; при необходимости станет модульной.
- `docs/preannotation.md` — руководство.
- `docs/modules/**` — модуль или справочник; вложенные `README.md` — тоже
  страницы модулей, а не точки входа.
- `docs/documentation.md` — мета-страница правил; вне типов страниц.
- `AGENTS.md` — инструкция агенту, вне пользовательской документации.

### Эмодзи

Для `#` выбирай эмодзи по теме страницы: `🐋` Docker, `🐍` Python, `🧱`
инфраструктура, `✅` проверки, `🏷️` метки, `📷` CV, `🧠` Keras, `🧰` utils,
`🎞️` видео, `📐` геометрия, `🤖` авторазметка, `📊` данные.

Для `##` используй стабильные обозначения для повторяющихся разделов:

- `🚀` — примеры, быстрый старт, запуск;
- `⚖️` — режимы правил;
- `⚠️` — ограничения;
- `🎛️` — флаги;
- `✅` — проверки;
- `🧪` — тесты;
- `📋` — результат;
- `🔧` — внутреннее устройство;
- `📚` — документация;
- `🧩` — каталог модулей и группы;
- `❓` — FAQ;
- `🗂️` — разделы и структура;
- `🧭` — навигация и концепция;
- `💡` — объяснение причин;
- `📦` — состав и содержимое;
- `🕸️` — граф зависимостей;

- `📥` — загрузка и получение;
- `📤` — экспорт и выгрузка;

Список не претендует на полноту: для остальных разделов выбирай эмодзи по
смыслу и переиспользуй существующие. Не вводи второй знак для того же
значения.

### README

- Заголовок — `# <эмодзи> <проект>: назначение`.
- После вступления — `## 🚀 Быстрый старт` с минимальными примерами.
- Каталог модулей — `## 🧩 Основные модули`; граф зависимостей остаётся
  внутри этого раздела в `<details>`.
- Дополнительные разделы (`Bash-скрипты`, `Docker`, `Предразметка`, `FAQ`)
  сохраняй, пока они полезны. FAQ и граф зависимостей могут быть в
  `<details>`; `<summary>` получает эмодзи как заголовок.
- README — единственная точка входа; второй общий `docs/README.md` не
  создавай. Вложенные `README.md` в `docs/modules/**` — страницы модулей.
- Исключения README: раздел ``## `>_` Bash-скрипты`` вместо эмодзи и `###` с
  эмодзи для смысловых подразделов и групп модулей.

### Исключения

- `docs/documentation.md` — мета-страница правил: не относится ни к одному
  типу, её структура следует логике правил.
- `docs/docker.md` пока остаётся руководством; если примеры станут основной
  формой, переведи страницу в модульный тип.
- Страницы чекеров могут добавлять разделы `🧪 Тесты` и `📋 Результат` после
  обязательных.
- Сторонние и сгенерированные Markdown-файлы правила не проверяют.
