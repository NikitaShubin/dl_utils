# 🧱 Линтинг инфраструктуры: check-infra.sh

Проверка `docker-compose`, `Dockerfile`/`*.Dockerfile`, shell-скриптов и
Markdown. Скрипт не требует Python.

## 🚀 Примеры

```bash
# Проверить весь проект
/path/to/dl_utils/check-infra.sh ~/my_project

# Проверить отдельные файлы и папки
./check-infra.sh docker docs README.md

# Включить правила проверяемого проекта
cd ~/my_project
/path/to/dl_utils/check-infra.sh -p .
```

`check-infra.sh` — часть набора из трёх чекеров с единым стилем вызова.
Общие цели, режимы, флаги и коды возврата описаны в
[«Общих правилах чекеров»](check-common.md); здесь — только специфика
инфраструктурного линтинга.

## 🔧 Что происходит внутри

Файлы ищутся по диску или берутся из `git ls-files`. Служебные каталоги
(`.git`, `__pycache__`, `.venv`, `node_modules`, `dist`, `build`, кеши)
пропускаются.

Поддерживаются:

- `docker-compose*.yml`, `docker-compose*.yaml`, `compose*.yml`,
  `compose*.yaml` — `dclint`;
- `Dockerfile`, `*.Dockerfile` — `hadolint`;
- `*.sh` — `shellcheck`;
- `*.md` — `markdownlint`.

Файлы других типов игнорируются. Для каждой категории запускается свой
линтер; файлы перечисляются по одному, диагностика линтера выводится сразу
после имени файла. Ошибка в одном файле не останавливает проверку остальных.

В стандартном режиме `.markdownlintignore` проверяемого проекта не
учитывается, чтобы он не исключал файлы из проверки. В проектном режиме
ignore-файлы действуют нативно.

## ⚠️ Ограничения

- `shellcheck` проверяет все файлы по правилам bash, поэтому POSIX `sh`-файлы
  могут получать замечания про bash-синтаксис.
- `markdownlint` проверяет длину строк (88 символов) и другие правила из
  `.markdownlint.yaml`; длинные ссылки и таблицы лучше переносить.
- Обычный поиск по большой файловой системе может занять время.
