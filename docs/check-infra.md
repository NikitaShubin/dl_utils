# 🧱 Линтинг инфраструктуры: check-infra.sh

Проверка `docker-compose`, `Dockerfile`/`*.Dockerfile`, shell-скриптов и
Markdown. Скрипт не требует Python.

## 🚀 Примеры

```bash
# Проверить весь проект
/path/to/dl_utils/check-infra.sh ~/my_project

# Проверить отдельные файлы и папки
./check-infra.sh docker docs README.md

# Включить правила проверяемого проекта
cd ~/my_project
/path/to/dl_utils/check-infra.sh -p .
```

Без путей проверяется текущая папка. Ошибка в одном файле не останавливает
остальные.

## ⚖️ Режимы правил

По умолчанию `dclint`, `hadolint` и `markdownlint` получают конфиги из
`dl_utils`, а ignore-файлы проверяемого проекта не действуют. Каждый файл
проверяется из своей директории.

Флаг `-p`/`--project-config` включает нативные правила проекта: инструменты
запускаются из каталога вызова и сами находят конфиги и ignore-файлы. Конфиги
не копируются и не смешиваются: за запуск отвечает только один источник
правил. Запускайте чекер из корня проекта, иначе инструменты найдут не те
конфиги.

Из-за особенностей ShellCheck в стандартном режиме его настройки из
`.shellcheckrc` для проверки внешних репозиториев повторно захардкожены в
`check-infra.sh`; их эквивалентность проверяется тестами репозитория. Поэтому
любое изменение `.shellcheckrc` должно сопровождаться изменением в чекере —
иначе проверка внешних проектов разойдётся с ожиданиями.

## 🎛️ Флаги

- `-f`, `--fix` — автофиксы `dclint` и `markdownlint`. `hadolint` и
  `shellcheck` только отчитываются.
- `-g`, `--git-only` — только закоммиченные файлы.
- `-c`, `--clean-cache` — принимается для совместимости с `check.sh`, на
  infra-проверки не влияет.
- `-p`, `--project-config` — нативные правила проекта вместо `dl_utils`.
- `-q`, `--quiet-no-files` — не печатать сообщение об отсутствии файлов,
  вернуть код `3`.
- `-H`, `--print-header` — печатать шапку с режимом и целями.

## 🔧 Что происходит внутри

Файлы ищутся по диску или берутся из `git ls-files`. Служебные каталоги
(`.git`, `__pycache__`, `.venv`, `node_modules`, `dist`, `build`, кеши)
пропускаются.

Поддерживаются:

- `docker-compose*.yml`, `docker-compose*.yaml`, `compose*.yml`,
  `compose*.yaml` — `dclint`;
- `Dockerfile`, `*.Dockerfile` — `hadolint`;
- `*.sh` — `shellcheck`;
- `*.md` — `markdownlint`.

Файлы других типов игнорируются. Для каждой категории запускается свой
линтер; файлы перечисляются по одному, диагностика линтера выводится сразу
после имени файла.

В стандартном режиме `.markdownlintignore` проверяемого проекта не
учитывается, чтобы он не исключал файлы из проверки. В проектном режиме
ignore-файлы действуют нативно.

## ⚠️ Ограничения

- Нужны установленные `dclint`, `hadolint`, `shellcheck` и `markdownlint`.
  Версии берутся из окружения; воспроизводимость обеспечивает Docker-образ.
- `hadolint` и `shellcheck` не умеют автофиксы; `-f` их не меняет.
- `shellcheck` проверяет все файлы по правилам bash, поэтому POSIX `sh`-файлы
  могут получать замечания про bash-синтаксис.
- `markdownlint` проверяет длину строк (88 символов) и другие правила из
  `.markdownlint.yaml`; длинные ссылки и таблицы лучше переносить.
- Вне git-репозитория `-g` не работает, а обычный поиск может занять время
  на большой файловой системе.
