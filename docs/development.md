# 🛠️ Разработка dl_utils

Правила, по которым репозиторий расширяется и проверяется. Они нужны, чтобы
новый модуль вписался в существующие зависимости и документацию.

## ➕ Добавить модуль

- Создайте плоский файл в корне `dl_utils`, например `my_utils.py`.
- Импортируйте зависимости абсолютными именами:

```python
from utils import mpmap
from cv_utils import BBox
```

- Добавьте docstring с назначением модуля и кратким описанием публичных
  функций.
- Создайте страницу `docs/modules/my_utils.md` по образцу соседних.
- Добавьте ссылку в каталог [корневого README](../README.md).
- Обновите граф зависимостей.
- Прогоните проверки.

Пакетную структуру с `__init__.py` для модулей библиотеки не используем: она
мешает вырезать отдельные модули и скрывает реальные зависимости. Служебный
пакет `checker/` — исключение: это код самих проверок.

## ✍️ Стиль кода

- Аннотации типов — современные: `str | int`, `list[int]`, без `Union` и
  `Optional`.
- Пути к файлам и папкам типизируйте как `str | Path`; при передаче в
  библиотеку, которая не принимает `Path`, используйте `os.fspath()`.
- В комментариях перед кодом ставьте двоеточие, в строке после кода — без
  знака, после комментируемого кода — точку.
- Предпочитайте короткие выражения: `|`, `:=`, comprehensions, `any`, `all`,
  `dict.get`/`setdefault`, `match/case`.
- Идентификаторы — английские, комментарии и документация — русские.

Полные правила собраны в [гайде по стилю](../AGENTS.md).

## 📓 Ноутбуки

Сохраняйте каноническую структуру JSON: `source` — список строк, каждая
строка кроме последней оканчивается `\n`, пустые строки — `"\n"`, а не `""`.
Иначе git показывает сотни изменений вместо нескольких. Ослабленные правила
для `.ipynb` задаются только в `pyproject.toml`, а не в коде чекера.

## ✅ Проверки

```bash
./check.sh my_utils.py docs/modules/my_utils.md
```

Или полный прогон с автофиксами:

```bash
./check.sh -f .
```

`-f` разрешает автофиксы. Без флага файлы не меняются. Флаги и общие правила
описаны в [справочнике чекеров](check-common.md), устройство — на страницах
инструментов.

## 🕸️ Граф зависимостей

Граф строится по фактическим импортам и сохраняется в `dependency_graph.mmd`:

```python
from utils import draw_repo_dependency_graph

draw_repo_dependency_graph()
```

Содержимое `dependency_graph.mmd` переносится в
[корневой README](../README.md). Это транзитивная редукция: если `A`
использует `B`, а `B` использует `C`, ребро `A → C` не рисуется.
Нарисованное ребро всегда означает прямой импорт, но не все прямые импорты
попадают в граф: часть из них заменена более длинным путём. Файлы с `_` в
начале имени исключены. После добавления или удаления импортов пересоберите
граф и обновите [корневой README](../README.md).

Граф остаётся в старом стиле Mermaid (`graph RL`): базовые модули слева,
прикладные справа. Узлы перечисляются по уровням зависимостей, для раскладки
используется ELK.

Если нужен Graphviz-рендер:

```python
from utils import draw_repo_dependency_graph_dot

draw_repo_dependency_graph_dot()
```

```bash
dot -Tsvg dependency_graph.dot -o dependency_graph.svg
```

Чтобы перенести модуль, недостаточно взять прямых соседей: нужны все файлы,
достижимые по стрелкам транзитивно. Например, `seg.py` напрямую зависит от
`cvat.py`, а `cvat.py` — от `video_utils.py`, поэтому `video_utils.py` тоже
нужен.

## 📚 Документация

Правила ведения документации — [docs/documentation.md](documentation.md).
Проектные особенности: не добавляйте разделы «Извлечение» — зависимости уже
перечислены в начале страницы; устаревшие модули удаляются, а не помечаются
статусами и бейджами.

## ⚠️ Ограничения

- Чекер не фиксирует версии инструментов: `ruff`, `mypy`, `pytest` и линтеры
  берутся из окружения. Для воспроизводимости запускайте проверки в
  Docker-образе; свежие версии — в актуальном образе.
- Полные проверки требуют `ruff`, `mypy`, `pytest`, `dclint`, `hadolint`,
  `shellcheck`, `markdownlint`. В минимальном окружении используйте
  Docker-образ.
- Граф не видит динамические импорты (`importlib`, `__import__`). Импорты
  внутри функций и условий попадают в граф пунктирными рёбрами.
- Страницы документации не тестируются автоматически; сигнатуры примеров
  проверяются вручную по исходнику.
