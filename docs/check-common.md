# 🧰 Общие правила чекеров

[`check.sh`](check.md), [`check-py.sh`](check-py.md) и
[`check-infra.sh`](check-infra.md) — один набор инструментов. У них единый
стиль вызова и общее поведение: одинаковые цели, режимы правил, флаги, коды
возврата и правила для тестов. Это сделано намеренно: у всех трёх один
интерфейс, чтобы не держать в голове разные правила для похожих задач. Чтобы
описание не расходилось, общая часть собрана здесь, а на страницах
инструментов остаётся только специфика.

## 🎯 Что проверяется

Без путей инструменты проверяют текущую папку. Исключение — Python-часть,
запущенная из корня `dl_utils`: она проверяет файлы из временного белого
списка `ROOT_FILES` в `checker/common.py`.

- `check-infra.sh` — проверяет текущую папку;
- `check-py.sh` — проверяет текущую папку; в корне `dl_utils` — файлы из
  `ROOT_FILES`;
- `check.sh` — проверяет текущую папку. В корне `dl_utils` Python-часть
  проверяет файлы из `ROOT_FILES`, infra-часть — всю папку.

`ROOT_FILES` — временный список. Кодовая база `dl_utils` постепенно
приводится к собственным стандартам, но многие файлы ещё ждут рефакторинга.
В список входят только уже адаптированные файлы. Когда переработка
завершится, список удалят, и `dl_utils` будет проверяться так же, как любая
другая папка.

Если передать пути, белый список не используется.

## 🧭 Откуда запускать

Текущая папка важна не только как место запуска:

- без путей она становится целью проверки (исключение — `ROOT_FILES`);
- с `-p` из неё запускаются инструменты, поэтому она определяет, какие
  конфиги и ignore-файлы они найдут.

`check.sh` передаёт свою текущую папку обоим подскриптам, так что правило
одинаково для всех.

Переданный путь не заменяет текущую папку. Например, при запуске
`check-py.sh -p ~/project/src` из `~/other` инструменты работают в `~/other`,
а не в `~/project`. Поэтому `-p` запускайте из корня проекта: иначе они могут
взять чужие настройки или не найти нужные. В стандартном режиме конфиги
заданы явно, поэтому текущая папка не меняет правила: `check-py.sh` запускает
линтеры из корня `dl_utils`, а `check-infra.sh` — из папки каждого файла.

`-g` ищет git-репозиторий по цели, а не по текущей папке.

## ⚖️ Режимы правил

По умолчанию чекеры используют конфиги `dl_utils`. Конфиги и ignore-файлы
проверяемого проекта не применяются: чужой проект не может ослабить проверку.
Встроенные подавления (`# noqa`, `# type: ignore`, `# shellcheck disable`)
работают.

Флаг `-p`/`--project-config` включает правила проекта. Инструменты запускаются
из текущей папки и сами находят конфиги, ignore-файлы, пользовательские и
глобальные настройки. Конфиги не смешиваются: действует только один источник
правил.

`check.sh` передаёт режим обеим частям. Python-часть использует `ruff` и
`mypy`, infra-часть — `dclint`, `hadolint` и `markdownlint`. `shellcheck` —
исключение: его настройки из `.shellcheckrc` продублированы в
`check-infra.sh`, а их совпадение проверяют тесты.

## 🎛️ Флаги

- `-f`, `--fix` — автофиксы. Умеют `ruff`, `dclint` и `markdownlint`;
  `hadolint` и `shellcheck` только отчитываются.
- `-g`, `--git-only` — проверять только файлы из `git ls-files`.
- `-c`, `--clean-cache` — удалить кеши `mypy`, `ruff` и `pytest`. На
  infra-проверки не влияет.
- `-p`, `--project-config` — правила проекта вместо `dl_utils`.
- `-q`, `--quiet-no-files` — не печатать сообщение об отсутствии файлов и
  вернуть код `3`. `check.sh` передаёт флаг подскриптам.
- `-H`, `--print-header` — печатать шапку с режимом и целями. `check.sh`
  передаёт флаг подскриптам.

## 🧪 Тесты

Тесты запускает только Python-часть: `check-py.sh` и `check.sh`. Они работают
по правилам проекта и не навязывают pytest-конфиг `dl_utils`. Ищутся файлы
`test_*.py` и `*_test.py`; нестандартный `python_files` не поддерживается.
Если тестов нет, `pytest` пропускается, а код `5` считается пропуском.
Покрытие информационное: порог не задаётся.

## 📋 Коды возврата

- `0` — ошибок нет. Если подходящих файлов нет и не задан `-q`, чекер
  предупреждает и тоже возвращает `0`.
- `1` — ошибки проверки или несуществующий путь.
- `2` — неизвестный флаг.
- `3` — нет файлов подходящего типа в режиме `-q`. `check.sh` считает это
  пропуском и возвращает `0`, если остальные проверки прошли.

## ⚠️ Ограничения

- Чекеры не устанавливают инструменты и зависимости проверяемого проекта:
  используются те, что есть в окружении. Воспроизводимость даёт Docker-образ.
- `-g` требует git-репозиторий: цель вне его — ошибка.
