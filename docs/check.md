# Скрипт [`check.sh`](../check.sh "Перейти к файлу")

Комбинированная проверка любого проекта: сначала
[check-py.sh](./check-py.md "Перейти к документации") (Python-код), затем
[check-infra.sh](./check-infra.md "Перейти к документации") (инфраструктура).
Аргументы передаются обоим подскриптам одинаково.

---

## Быстрый старт: чужой проект

```bash
cd ~/my_project && /path/to/dl_utils/check.sh
```

Без аргументов из любой папки, кроме корня dl_utils, скрипт проверяет саму
эту папку. Можно и не заходить внутрь — достаточно передать путь:

```bash
/path/to/dl_utils/check.sh ~/my_project
```

---

## Режимы запуска

| Запуск                      | Что проверяется                       |
| :-------------------------: | :-----------------------------------: |
| с явными путями             | только указанные цели                 |
| без путей из чужой папки    | содержимое текущей папки              |
| из корня dl_utils без путей | белый список py и ipynb + infra       |

Пути могут быть файлами или папками (несколько — через пробел).

## Как маршрутизируются файлы

`check.sh` не определяет тип файла сам — он выводит их на оба подскрипта
с флагами тишины и шапки (`-q -H`). Каждый подскрипт проверяет только свои
релевантные файлы и молчит, если таких нет:

- `.py` / `.ipynb` → `check-py.sh`;
- `Dockerfile` / `docker-compose*.yml|yaml` / `compose*.yml|yaml` / `*.sh` / `*.md`
  → `check-infra.sh`.

Тем самым переданный одиночный файл попадает только к подходящему чекеру.
Код возврата `3` подскрипта означает «не нашёл файлов подходящего типа» —
это не ошибка. Главный `check.sh` проверяет, что хоть один подскрипт что-то
нашёл и проверил: если ни один не нашёл (например, передан `.txt`) — вывод
предупреждения и код `0`.

## Флаги

<!-- markdownlint-disable MD013 -->
- `-f`, `--fix` — разрешить автофиксы в обоих скриптах (ruff format/check
  в check-py.sh, dclint/markdownlint в check-infra.sh);
<!-- markdownlint-enable MD013 -->
- `-g`, `--git-only` — проверять только закоммиченные в git файлы (удобно
  для CI); цель вне репозитория считается ошибкой.

По умолчанию действует режим отчёта: проблемы фиксируются в выводе и влияют
на код возврата, но файлы не изменяются. Неизвестные флаги завершают скрипт
с кодом 2 и краткой справкой (`--help`).

## Конвейер

1. запуск `check-py.sh` — ruff format → ruff check → mypy (включая
   `.ipynb` через `nbqa`) → pytest;
2. запуск `check-infra.sh` — dclint → hadolint → shellcheck → markdownlint;
3. общий вердикт.

Каждый подскрипт печатает собственную шапку (`▶ check-xxx.sh`) только когда
что-то реально проверил; если он не нашёл файлов подходящего типа, он в
режиме тишины (`-q`) молчит и отдаёт код `3`. `check.sh` агрегирует:

- хоть один подскрипт проверил файлы, ошибок нет → код `0`;
- есть ошибки → код `1`;
- ни один подскрипт не нашёл файлов (например, передан `.txt`) → предупреждение,
  код `0`.

---

## Визуальное разделение вывода

`check.sh` обрамляет в прямоугольники только общий вердикт; шапки головного
скрипта, рамки по каждому чекеру — их теперь печатают сами подскрипты
(при `-H`), и только когда есть что проверять:

- **Cyan-прямоугольник** — шапка подскрипта (`▶ check-py.sh`, `▶ check-infra.sh`);
- **Зелёный прямоугольник** — итог успешен (`✓ ИТОГ: все проверки пройдены`);
- **Красный прямоугольник** — итог с ошибкой (`✗ ИТОГ: ошибки`);
- **Жёлтый прямоугольник** — предупреждение, нет файлов подходящего типа
  (`⚠ ИТОГ: нет файлов подходящего типа`).

Вывод подчинённых чекеров идёт без рамок (как при отдельном запуске), внутри —
псевдографические разделители (`═`) для отделения этапов. Лаконичный вывод в
стиле `infra`: на каждый файл одна строка `▸ файл`, ошибки — только там, где
есть.

## Примеры

```bash
./check.sh ../other_project    # чужой проект целиком
./check.sh src module.py       # папка плюс отдельный файл
cd ../other_project && ./dl_utils/check.sh  # то же изнутри проекта
./check.sh -f src              # проверка с автофиксами
./check.sh -g .                # только закоммиченное (для CI)
./check.sh                     # белый список py/ipynb + текущая папка infra
```
