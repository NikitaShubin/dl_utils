# ✅ Проверка кода: check.sh

Комбинированная проверка Python и инфраструктуры: `check-py.sh` и
`check-infra.sh` подряд. Аргументы передаются обоим скриптам.

## ⚖️ Режимы правил

По умолчанию действует стандартная проверка `dl_utils`: `ruff`, `mypy` и
infra-линтеры получают конфиги из `dl_utils`, а конфиги и ignore-файлы
проверяемого проекта не применяются. Так чужой проект не может ослабить
аудит своими настройками. Встроенные подавления (`# noqa`, `# type: ignore`,
`# shellcheck disable`) при этом работают.

Флаг `-p`/`--project-config` включает нативные правила проекта: каждый
инструмент запускается так, как если бы его вызвали вручную из текущей папки.
Он сам находит конфиги проекта, пользовательские и глобальные настройки,
ignore-файлы. Конфиги не копируются и не смешиваются: за запуск отвечает
только один источник правил.

Проектный режим отсчитывается от каталога вызова, а не от переданного пути.
Запускайте чекер из корня проекта:

```bash
cd ~/my_project
/path/to/dl_utils/check.sh -p .
```

Это эквивалентно отдельному запуску `ruff`, `mypy`, `pytest` и infra-линтеров
из этой папки с их собственными правилами.

`shellcheck` — единственное исключение: его настройки из `.shellcheckrc`
продублированы в `check-infra.sh`, а их эквивалентность проверяется тестами;
изменения конфига должны попадать и в чекер.

## ✅ Проверить свой проект

```bash
/path/to/dl_utils/check.sh
```

Без путей из любой папки, кроме корня `dl_utils`, проверяется эта папка.
Можно передать путь явно:

```bash
/path/to/dl_utils/check.sh ~/my_project
```

## ✅ Проверить отдельные файлы

```bash
./check.sh src module.py docker/Dockerfile README.md
```

`check.sh` передаёт цели обоим подскриптам. Каждый берёт только свои типы
файлов:

- `.py`, `.ipynb` → `check-py.sh`;
- `Dockerfile`, `*.Dockerfile`, `docker-compose*.yml`,
  `docker-compose*.yaml`, `compose*.yml`, `compose*.yaml`, `*.sh`, `*.md` →
  `check-infra.sh`.

Если ни один подскрипт не нашёл подходящих файлов, выводится предупреждение
и код `0`.

## 🧪 Тесты

Тесты принадлежат проекту и в обоих режимах запускаются по его правилам:
`dl_utils` не навязывает pytest-конфиг. Тесты ищутся по именам `test_*.py` и
`*_test.py`; нестандартный `python_files` не поддерживается. Если тестов нет,
`pytest` пропускается, а код `5` (тесты не собраны) считается пропуском.
Покрытие информационное: порог не задаётся.

## 🎛️ Флаги

```bash
./check.sh -f src      # автоисправления
./check.sh -g .        # только закоммиченное в git
./check.sh -c .        # очистить кеши инструментов
./check.sh -p .        # правила проекта вместо dl_utils
```

- `-f`, `--fix` — разрешить автофиксы (ruff format/check, dclint,
  markdownlint). По умолчанию файлы не изменяются.
- `-g`, `--git-only` — проверять только файлы из `git ls-files`.
- `-c`, `--clean-cache` — удалить кеши mypy/ruff/pytest перед прогоном.
  На infra-проверки не влияет.
- `-p`, `--project-config` — нативные правила проекта.

## 📋 Результат

- `0` — ошибок нет;
- `1` — хотя бы один чекер нашёл проблемы или путь не существует;
- `2` — неизвестный флаг.

Этапы идут последовательно: сначала Python, затем инфраструктура. Падение
одного этапа не отменяет второй, но итоговый код будет `1`. Python-часть
выполняет [check-py.sh](check-py.md) (pytest с покрытием, ruff, mypy),
инфраструктурную — [check-infra.sh](check-infra.md) (Docker, shell и Markdown).

## ⚠️ Ограничения

- Для проверки нужны сами инструменты: `ruff`, `mypy`, `pytest`, `dclint`,
  `hadolint`, `shellcheck`, `markdownlint`. Чекер не устанавливает и не
  закрепляет их версии: используются те, что есть в окружении.
  Воспроизводимость обеспечивает Docker-образ.
- `-g` требует git-репозиторий; цель вне репозитория считается ошибкой.
- Скрипт не устанавливает зависимости проверяемого проекта. Если проект не
  импортируется, mypy и pytest упадут.
